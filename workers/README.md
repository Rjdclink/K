# Remote workers while retaining Neon

The worker keeps the dashboard, database, records, API quota coordination and
existing order ledger on Neon. It can move the existing scanner, verification,
exit monitoring and combination processing into one real remote Node process.
It imports the same `src/index.mjs`; there is no second copy of the strategies.

This adapts the user's Bad-Blue Computational Beam design (source commit
`8bae7c0d7bd106f89a1b93242ff9410f98302ff9`): ordered light Antenna tasks,
bounded Beam scheduling, task priority, rejection of expired queued work,
cancellation and measured execution telemetry. It adds real host execution and
database-fenced ownership. No claimed remote capacity is invented.

The code is a deployable foundation. It does not create a hosting account or
provision a server. No new host is currently configured. Cost and speed gains
have not been established. A free host must have sufficient CPU, memory,
network allowance and availability for the workload. More worker replicas
are not assumed to save money or improve speed.

## Build and test

Use Node 24 and run `npm ci`, `npm test`, and `npm run build`.
The container definition is `workers/Dockerfile`, with the repository root as
its build context. No environment files or credentials are copied into it.

`npm run worker` defaults to `K_WORKER_ROLE=probe`: it measures seven public
Kalshi status reads, then serves `/health` on `PORT` (default 8080). It does not
load the trading engine or connect to the database. `npm run worker:probe` runs
the same public probe once and exits. These status timings describe the host's
connection, not order fills or bill savings.

The worker exposes only a health endpoint. Scanner, sale, dashboard and order
endpoints are not exposed by its HTTP server. Use the host's HTTPS endpoint for
health checks; the cloud platform or a reverse proxy terminates TLS.

## Prepare an actual host

Choose a real free or lower-cost host before activation. Set sensitive values
with the host's private secret mechanism; never commit or paste them into logs.
The active runtime needs the existing `DATABASE_URL`, Kalshi key ID/private key,
trading switches, and any existing optional AI configuration it relies on.
Retain the current `LIVE_TRADING` / `EXIT_ONLY` settings rather than enabling
trading merely to test a host. It uses the same push identity and Neon records.

Set `K_WORKER_ID` to one stable identifier (letters, digits, dot, underscore or
hyphen), `K_WORKER_ROLE=active`, and `K_SOURCE_REVISION` to the deployed commit.
The active role still cannot scan until the database assigns it ownership.
Starting a standby worker does not take the lock away from Neon cron. Only one
assigned worker ID and one process can own a scanning window at a time.

## Measure before handing over work

1. Deploy this worker-aware source to the existing Neon function, preserving its
   environment. `/health` must report `scannerRuntimeProtocol: 1`.
2. With the existing private database connection configured, run
   `npm run worker:control -- init`. This installs the small ownership table with
   **Neon as the default owner**; it does not move or delete any existing data.
3. Collect the Neon baseline with an authenticated, same-origin POST to
   `/api/worker-benchmark`. It runs a fixed read-only exchange/database chain
   seven times through the existing quota limiter. It creates no signals,
   funding transfers, RFQs or orders.
4. On the candidate host, run `npm run worker:benchmark` with its intended private
   environment. This runs that identical read-only chain and exits. Collect both
   reports under comparable traffic conditions. Include all remaining Neon,
   worker-hosting, storage and network charges in cost projections for the same
   period. Free compute alone does not prove the total cost is zero.
5. Store a private JSON document with `baseline` and `candidate` objects. Each
   contains its measured report plus `projectionPeriodHours` and
   `totalOperatingUsd`. These added cost numbers are projections based on current
   usage and confirmed provider allowances, not measurements generated by the
   timing benchmark. Baseline `runtimeId` must be `neon`; candidate `runtimeId`
   must match `K_WORKER_ID`. Reports must be less than 24 hours old. There are no
   invented example readings or preapproved savings in this repository.

`workers/readiness.mjs` rejects a handoff when the evidence is missing, simulated,
stale, projects no lower total cost, or fails to show both faster Kalshi
communication and a faster complete read-only exchange/database path. This
does not certify order-fill speed or future bills. Confirm actual bills after
cutover, including any change in Neon database usage.

## Handoff and recovery

After successful measurements, set `K_NEON_URL` to the existing dashboard URL
and `K_WORKER_URL` to the candidate host's HTTPS URL. Run:

```sh
npm run worker:control -- worker remote-1 /private/path/evidence.json
```

Use the actual configured worker ID in place of `remote-1`. This verifies Neon
and worker health and the measurement document, then waits for the existing
scanner's session lock before changing ownership. Neon cron subsequently skips
scanning instead of duplicating the remote work. The dashboard and database
remain on Neon. All existing contract, quote, fee, allocation, timing, external
verification and final order-idempotency gates remain in force.

To return scanning to Neon, stop the remote worker and run:

```sh
npm run worker:control -- neon
```

The handoff waits for any old scan and its queued combination work to finish.
A disconnected runtime loses its session lock, and its scanner context rejects
further exchange writes. Existing uncertain-order reconciliation still handles
an exchange request interrupted after dispatch. No automatic fallback starts a
second scanner; supervise/restart the worker and monitor health. Never run the
older worker-unaware Neon code while remote ownership is enabled.
